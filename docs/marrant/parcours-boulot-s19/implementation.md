### B1 (commun design et ux) : étape 1 visiteur sans conseil, exemple ni défi

**Cause (prouvée)** : le HTML partagé (ISR) de `/parcours/<slug>` est pré-rendu au build. Si le parcours n'est pas **actif en base** à ce moment, `findActivePath` ne le trouve pas et la page prend le repli `buildPathFromSeed` (`lib/parcours-data.ts`), qui posait `tip.content = moduleDetail` (masqué par la règle T28 de la carte), `example = ""`, `exercise = ""`. La page reste ainsi jusqu'à la première régénération (`revalidate = 3600`), et le visiteur, qui ne rappelait jamais l'API, ne voyait jamais mieux. C'est exactement l'ordre de la prod : le build qui porte `BOULOT_PUBLIE = true` précède la tâche de démarrage qui passe `isActive` à `true`. Preuve au run du 11/10 (ordre prod, `captures.sh`) : « base avant build : isActive=false », « pré-rendu du build : repli seed (seed-boulot) », et le HTML servi porte `seed-boulot`. Contre-épreuve (`QA_ORDRE=active-avant-build QA_SANS_CAPTURES=1`) : parcours activé en base avant le build, « pré-rendu du build : base ». Les captures de l'itération 1 viennent donc d'un build où le parcours n'était pas actif en base [HYPOTHÈSE : run lancé avec `--sans-inactif`, qui saute la création du parcours ; l'`UPDATE` d'activation ne touchait alors aucune ligne] ; le risque, lui, est celui de la prod quel que soit le run.
