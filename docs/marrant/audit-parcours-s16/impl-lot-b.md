## Recos traitées

- **14, limitation de débit partagée** : `lib/rate-limit.ts` ajoute `sharedRateLimit(scope, clé, {max, fenêtre})`, un compteur Postgres partagé entre tous les isolats (table existante `JobLock`, lignes `rl:<scope>:<sha256 de la clé>:<uuid>`, fenêtre glissante exacte, purge des lignes expirées à chaque appel, aucune donnée personnelle en base). Si la base tombe, repli sur le compteur mémoire, donc pas de blocage global. `getClientIp` lit **`cf-connecting-ip` uniquement** (`x-forwarded-for` ignoré, valeur `local` hors Cloudflare). `retryAfterSeconds` sert l'en-tête `Retry-After`. Le binding Workers Rate Limiting n'a pas été retenu : périodes de 10 ou 60 s seulement, compteur par point de présence. Le `rateLimit` mémoire reste pour les appelants des autres lots. Limites appliquées : login 10 essais / 15 min par e-mail + 30 / 15 min par IP (`auth.ts`) ; register 5 / h par IP ; forgot 3 / h par IP ; reset 10 / 15 min par IP (nouveau). 429 + `Retry-After` sur les routes.
- **15, jeton de réinitialisation** : `lib/reset-token.ts` (nouveau). Seul le hash SHA-256 est stocké dans `VerificationToken.token`, et la comparaison se fait sur le hash (`forgot-password/route.ts`, `reset-password/route.ts`). Le filtre Umami vient de `lib/umami-before-send.ts` (nouveau, branché dans `app/layout.tsx`) : sur /reset-password, toute la query string est retirée ; ailleurs, les paramètres `token` et `email` sont retirés, dans `url` **et** `referrer` (Umami reprend l'URL précédente comme référent). /blog/apercu reste coupé. `reset-password/layout.tsx` passe en `referrer: no-referrer`. Plus aucun e-mail dans les logs d'`auth.ts` (identifiant utilisateur à la place, y compris pour `createUser`).
- **13, liaison Google** : `allowDangerousEmailAccountLinking` est retiré. Sur /login, `OAuthAccountNotLinked` affiche un message clair, et la relance automatique de Google, qui bouclait, est supprimée. Le logger NextAuth appelle `recordAuthFailureAlert` (lot A, clé `auth-connexion-google`, classe A) sur tout code `*OAUTH*`, maintenu en vie par `ctx.waitUntil` sous Workers. `OAuthAccountNotLinked` n'est pas journalisé par NextAuth : il est donc mesuré par Umami et ne déclenche pas d'alerte.
- **16, connexion** : `authorizeCredentials` (exporté, testable) lève des codes distincts : `TropDEssais`, `CompteGoogleSansMotDePasse`, `ErreurServeurConnexion`. Des identifiants faux renvoient `null`, qui devient `CredentialsSignin`. /login associe un message à chaque code. L'événement Umami `connexion-echec {methode: email|google, motif}` est émis, avec ces motifs : identifiants, trop-d-essais, compte-google, serveur, reseau, compte-mot-de-passe, ou le code OAuth. Les messages « Erreur serveur », « Données invalides » et « Email requis » des routes auth et user sont remplacés par des textes humains (`details` est conservé pour les erreurs par champ de /register).
- **19 (partie)** : après un échec, l'e-mail est gardé, le mot de passe est vidé et le focus revient sur le champ utile (mot de passe, ou bouton Google pour un compte Google). L'en-tête mobile anonyme affiche « Connexion » sans ouvrir le menu : texte dès 400 px, icône avec nom accessible « Connexion » de 360 à 399 px, et le lien reste dans le menu sous 360 px. Pour faire la place, le logo passe en `text-lg` sous 640 px et l'écart en `gap-2`. Sur /reset-password : bouton afficher / masquer, `autocomplete="new-password"` sur les 2 champs, erreur en `role=alert` reliée par `aria-describedby`.
- **5, suppression de compte** : `DELETE /api/user` exige une session et le mot « SUPPRIMER » retapé (revérifié par zod, casse et espaces ignorés). La route appelle `lib/account.ts#deleteAccount` (nouveau) : d'abord la résiliation **immédiate** chez Stripe via `cancelStripeSubscriptionNow` (lot A, idempotent, D2), pour l'abonnement connu **et** tout autre abonnement encore facturant de ce client Stripe. Si Stripe échoue, rien n'est supprimé (502). Ensuite, une transaction efface les jetons de reset, la fiche `CeoLead`, l'inscription newsletter et l'utilisateur (le reste suit en cascade). Les cookies de session sont effacés, puis `signOut` côté client. Dans `auth.ts`, un JWT dont l'utilisateur n'existe plus est invalidé au rafraîchissement suivant. Le client Stripe et ses factures restent chez Stripe (obligation comptable). UI : `components/profil/supprimer-compte-card.tsx`, événement Umami `compte-supprime {abonne}`.
- **11, profil** : `GET /api/user/subscription` renvoie la formule, le prix réel, l'échéance, `cancelAtPeriodEnd`, `hasPortal` et `hasStripeSubscription`. La source est la base, complétée par une lecture Stripe si l'abonnement est ancien. `POST /api/user/subscription/portal {parcours: changer-formule|resilier|carte}` crée une session de portail ciblée (`subscription_update`, `subscription_cancel`, `payment_method_update`), avec repli automatique sur le portail simple si la configuration refuse le parcours. UI : `components/profil/abonnement-card.tsx` + `hooks/use-subscription-summary.ts`, qui sortent la carte de `profil-dashboard.tsx` (419 → 353 lignes). Ce qui s'affiche : formule et prix, « Prochain prélèvement le … », « Premium jusqu'au … » après résiliation. En impayé (PAST_DUE) : badge « Paiement refusé », message et bouton « Mettre à jour ma carte », sans offre de ré-abonnement. Un seul bouton « Résilier mon abonnement », qui précise jusqu'à quand l'accès reste. Le bouton « Changer de formule » s'accompagne de l'argument D5 pour l'annuel. Le prix « S'abonner à … » vient de `config/premium` et l'erreur serveur du checkout (409) est affichée.
